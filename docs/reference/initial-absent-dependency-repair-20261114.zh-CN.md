# 首次缺失的本地依赖：源码修复与验证进度

14.3 的实际客户端已经复现过这个问题：打开工程时本地 `replace` 目录不存在，后来补齐目录和源码，Go 命令能正常运行，编辑器却仍保留旧的导入错误。原始失败记录继续保留。本次完成了源码修复和测试，**新代码尚未经过独立客户端验收，也尚未发布新安装包**。

修复后，IDE 会先让工程选择的 Go SDK 判断失败的导入属于哪个已选中的本地模块。只有这个模块的确切目录会成为恢复候选；没有被工程使用的 `replace` 声明、vendor 中未使用的原目录和宽泛父目录不会因此被监听。不存在的目录只做有界状态检查，不会被算作已经取得文件监听。

目录出现后，再查询一次真实的 Go 信息；即使这次查询碰到临时错误，也保留同一使用者的重试机会。切换 SDK、普通输入失效、关闭最后一个使用者和停止服务仍会撤回旧候选。一个新目录被拒绝，不会挡住其他可用目录；已经取得的监听按实际使用者保留，完整依赖图只在需要的目录全部取得实际覆盖后才提交。

另一个真实平台测试暴露了分批写入目录的缺口：先创建空依赖目录、再写 `go.mod`、最后创建深层源码时，Go 已能读到源码，平台文件缓存却还没有加载它。现在收到已持有范围内的新目录事件后，会在后台补充加载。继续使用原有的20,000条目、64层深度、路径和符号链接限制；排除 VCS 子树，不刷新外部父目录，也不每两秒遍历整棵树。扩展失败时保留已有文件的刷新，但标记覆盖不完整，并对扩展单独退避30秒。候选与已持有目录共享128根上限。
